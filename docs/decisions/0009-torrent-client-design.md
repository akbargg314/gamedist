# 0009. Launcher BitTorrent client: untrusted torrents, verified chunks

Status: Accepted

## Context

PLAN §5 asks for a launcher transport toggle (direct / torrent + direct /
torrent only), optional seeding, and a download engine in which "HTTP fills
the missing pieces". ADR 0002 fixed the torrent format the server generates:
BitTorrent v1, one multi-file torrent per release platform named `files`,
with a BEP 19 web seed.

Constraints:

- Torrents are generated by the server and are **not signed**. Info hashes are
  published in the release list, outside the signed manifest. A malicious
  server can hand out any torrent, and peers are anonymous.
- v1 pieces span file boundaries and do not line up with GameDist chunks, so
  SHA-1 piece checks cannot replace BLAKE3 chunk verification.
- librqbit (MIT), the torrent library named in the plan, has no BEP 19
  web-seed client, so it cannot mix HTTP into the swarm download itself.
- A torrent client that is pointed at an existing directory "repairs" it to
  match the torrent. Pointing it at an install directory would let unsigned
  data overwrite verified game files.

## Decision

- BitTorrent is the `torrent` cargo feature of `gamedist-launcher` (on by
  default), using librqbit with one session per launcher process. DHT, local
  service discovery and UPnP are disabled; peers come only from the trackers
  named in the torrent, normally the server's HTTP tracker at `/announce`.
  The session listens on TCP (`listen_port`, 0 = any free port).
- The `transport` setting is `direct` (default), `torrent-direct` or
  `torrent`.
- **Accepting a torrent.** The launcher fetches the torrent only from the host
  it is installing from and accepts it only if the info dictionary is exactly
  `{files, name = "files", piece length, pieces}` and its file list (paths,
  order, sizes) is identical to the signed manifest's platform. Anything
  else, such as extra members, a different name or different paths, is
  rejected.
- **Downloading.** The files that the install plan will write are downloaded
  into a scratch directory under the launcher's data directory, never into
  the install directory. The torrent phase ends when the download completes
  or makes no progress for `torrent_stall_secs` (default 20). Chunks are then
  lifted out of the scratch files one by one, each verified against its
  BLAKE3 ID from the signed manifest, exactly like chunks downloaded over
  HTTP, and the scratch directory is deleted.
- **Filling gaps.** After the torrent phase, chunks that are still missing are
  fetched over HTTP from the game's sources (`torrent-direct`), or the install
  fails (`torrent`). If no usable torrent exists, `torrent-direct` uses HTTP
  directly. HTTP therefore fills gaps at the chunk level after the swarm
  phase, not piece by piece during it.
- **Seeding.** An install directory is seeded only after `verify_tree` passes
  against the signed manifest **and** the SHA-1 piece hashes recomputed
  locally from the installed files equal the torrent's `pieces`. The torrent
  is added paused and is unpaused only if the client also sees the data as
  complete, so the client never has anything to write into the install
  directory. Seeding of a game stops before the game is updated, repaired or
  uninstalled. `gamedist-launcher --headless seed` seeds every installed game
  until Ctrl-C.
- The bandwidth limit applies to the torrent session as well as to HTTP;
  `upload_limit` caps uploads.

## Consequences

- Integrity does not depend on torrents, trackers or peers: everything that
  reaches an install directory has been checked against the signed manifest.
  The torrent client cannot write into an install directory.
- The trade-off is disk and I/O: torrent data is written to the scratch
  directory and then copied into the content store and the install tree, so
  a torrent install temporarily needs extra space.
- HTTP does not take over while the swarm is merely slow; it starts only after
  the torrent phase completes or stalls for `torrent_stall_secs`. A swarm that
  keeps trickling data keeps the torrent phase going.
- A server that publishes a bad torrent, or none, only disables the torrent
  path for its releases; `torrent-direct` still installs over HTTP.
- Without DHT, players find each other only through the trackers in the
  torrent. A server with `tracker = false` and no `external_trackers` gives
  launchers no way to find peers.
- Settings read by the torrent session (bandwidth and upload limits, listen
  port) take effect when the session starts, i.e. on the next launcher start.
- A BEP 19 web-seed client, hybrid v2 torrents and finer-grained mixing of
  HTTP and torrent downloads can be added later without changing the
  protocol.
- The end-to-end test `torrent_swarm_between_two_launchers` covers the swarm
  (a second launcher gets at least half of the data from the first), the
  torrent-only transport, the fallback to HTTP with no seeders, and the
  refusal to seed a modified install.
