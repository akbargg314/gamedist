# Security model

GameDist assumes **servers are untrusted for integrity**. Trust is rooted in
the developer's Ed25519 key and pinned by the launcher on first install.

Client-side checks described here are protocol requirements (SPEC §3, §4.3,
§6). The verification primitives (signatures, Game ID, paths, chunk hashes,
rotation chains, atomic assembly) are implemented in `gamedist-core`; the
launcher engine (`crates/launcher`) applies them, including key pinning,
key-change refusal and rollback protection. The end-to-end tests in
`tests/e2e` show that a corrupted chunk, a swapped developer key and a
rolled-back channel are refused.

## Actors and assets

| Actor | Trusted for |
|---|---|
| Developer key holder | Content and versions of their game |
| Distributor server | Availability only |
| CDN, mirrors, torrent peers | Nothing (every byte is verified) |
| Launcher | Enforcing the checks below on the player's machine |

## What a malicious or compromised server can do

- **Withhold** — refuse to serve a game, a version or chunks, or go offline.
  Mitigation: mirrors on other hosts and torrent peers; the same Game ID is
  recognised everywhere.
- **Serve stale but genuinely signed releases** — point a channel at an older
  version, or hide newer ones. The launcher refuses to move an install to a
  lower version than the one installed unless the player asks (rollback
  protection, SPEC §3.1), so a server can freeze updates but not downgrade an
  existing install. It can still offer an old signed version to a new player.
- **Alter unsigned metadata** — the game manifest (title, summary,
  description, store-page images, channel pointers) is generated by the server
  and not signed. A server can change the store page or show misleading text.
  It cannot change what gets installed.
- **Collect metadata** — IP addresses of players and peers, what they
  download. Use a server you trust for privacy, or a VPN/torrent settings that
  suit you.
- **Claim a slug with someone else's public key** — registering a public key
  on a server does not prove possession of the private key (this is what lets
  anyone mirror a game). A party that does this controls the unsigned metadata
  on that server, but can only publish releases the developer actually signed.

## What it cannot do

- **Forge or modify a release.** Release manifests are signed (Ed25519 over
  RFC 8785 canonical JSON, strict verification). The server verifies the
  signature on publish, and the launcher verifies it again against the
  **pinned** key, not the key the server claims.
- **Swap the developer key silently.** A release signed by any other key is
  refused unless a valid rotation chain signed by the pinned key exists, or
  the player explicitly accepts the hard key-change warning.
- **Fake a Game ID.** The launcher recomputes it from `developer_pubkey` and
  `slug` and rejects a mismatch.
- **Corrupt files.** Every chunk is identified by its BLAKE3 hash; the
  launcher (and the server on upload) verifies each chunk before writing it to
  its final location, writing to a temp file and renaming atomically.
  Torrents are unsigned, so data received over BitTorrent is verified against
  the signed manifest chunk by chunk, too (see below).
- **Hold developer keys.** Servers never see private keys. API tokens only
  authorise uploads and metadata changes.

## BitTorrent

Torrents are generated by the server and are not signed, and torrent peers
are anonymous, so the launcher trusts neither:

- It fetches a release's torrent only from the host it is installing from,
  and accepts it only if the info dictionary contains exactly `files`,
  `name` (which must be `files`), `piece length` and `pieces`, and the file
  list (paths, order, sizes) is identical to the signed manifest's. A torrent
  with extra members, another name, or different paths (including `..`
  tricks) is rejected.
- Downloaded data goes to a scratch directory, never into an install
  directory. Chunks are lifted out of it one at a time and each is kept only
  if it matches its BLAKE3 ID from the signed manifest; anything else is
  discarded and fetched over HTTP (or the install fails, with the
  torrent-only transport). The SHA-1 piece hashes of the torrent are not
  relied on for integrity.
- An install directory is seeded only after it has passed full verification
  against the signed manifest and its locally recomputed SHA-1 piece hashes
  equal the torrent's. The torrent client then considers the data complete
  and has nothing to write, so a bad torrent cannot make it "repair" an
  install with unsigned data.
- DHT and local peer discovery are disabled; peers come from the trackers
  named in the torrent. Peers and trackers see your IP address and which
  release you download or seed. Seeding is off by default.

A malicious server or peer can therefore waste bandwidth or slow a torrent
download down, but cannot get unverified data installed. The torrent phase
ends only when it is complete or has made no progress for
`torrent_stall_secs`; a swarm that keeps trickling data can keep it going, in
which case switch the transport back to `direct`.

## Path traversal and filesystem safety

Manifest paths are untrusted input. Before touching disk, consumers enforce
(SPEC §4.3): relative paths only, `/` separators, NFC-normalised; no empty,
`.` or `..` components; no backslash, no `:` (drive letters, NTFS alternate
data streams), no control characters, no component ending in a space or dot,
no Windows reserved device names (`CON`, `NUL`, `COM1`, …); paths unique
case-insensitively; launch `exe` must be a listed file. During assembly the
installer refuses to write through symlinks (`paths::join_no_symlinks` in
`gamedist-core`), and the CLI refuses to publish builds that contain symlinks.
File modes are reduced to `0644` or `0755`.

## Size and resource limits

Chunks are at most 8 MiB; a file's size must equal the sum of its chunks and
`total_size` the sum of files, so a manifest cannot declare one size and
deliver another. Signed objects contain only integers within ±(2^53−1). The
server caps request bodies (8 MiB + 1 KiB for chunks, 64 MiB for manifests),
rate-limits authentication and uploads per IP, and enforces per-account
storage quotas.

## Server-side account security

- Passwords are hashed with Argon2; at least 10 characters.
- API tokens are stored hashed; the CLI keeps them in the OS keyring (or a
  0600 file) and never logs them.
- The portal uses `HttpOnly`, `SameSite=Lax` session cookies with CSRF tokens
  on forms.
- Admin actions (users, settings, invites, takedowns, rotations) are recorded
  in the audit log.

## Residual risks

- **Trust on first use**: a player whose first install comes from a malicious
  server, of a game signed by the attacker's key, pins the attacker's key.
  Share links from the developer's own site, and compare the key shown by the
  launcher with the one the developer publishes.
- **Key compromise**: whoever holds the developer key can publish updates.
  Keep it offline; see [Key rotation](key-rotation.md).
- **Executing games**: GameDist verifies that you run what the developer
  signed, not that the developer is benign. Games run with your user's
  permissions.

## Reporting vulnerabilities

Please report security issues privately to the maintainers rather than in a
public issue.
