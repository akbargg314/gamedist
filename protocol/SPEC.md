# GameDist Protocol v0

Status: **draft, authoritative for `gamedist/0`**. The key words MUST, SHOULD and MAY are used as in RFC 2119.

GameDist distributes games as content-addressed chunks described by a
developer-signed release manifest. Any HTTP server can host a game; the server
is never trusted with integrity. Trust is rooted in the developer's Ed25519 key.

## 1. Identifiers

| Name | Form |
|---|---|
| Slug | `[a-z0-9][a-z0-9-]{1,63}` |
| Game URL | `https://<host>/games/<slug>` |
| Install URI | `gamedist://<host>/games/<slug>` (equivalent to the `https` URL). `gamedist+http://` maps to plain `http` and is intended for local development only. |
| Public key | `ed25519:<base64url, no padding, of the 32 raw key bytes>` |
| Game ID | first 26 characters of lowercase, unpadded RFC 4648 base32 of `SHA-256(pubkey_raw_32_bytes ‖ slug_utf8)` |
| Chunk ID | 64 lowercase hex characters: BLAKE3-256 of the raw (decoded) chunk bytes |
| Version | Semantic Versioning 2.0.0 (`1.2.0`, `1.3.0-beta.1`). Build metadata (`+…`) is not allowed. |
| Platform | `<os>-<arch>`, e.g. `windows-x86_64`, `linux-x86_64`, `linux-aarch64`, `macos-aarch64`, `macos-x86_64`. Pattern `[a-z0-9]+-[a-z0-9_]+`. |
| Channel | `[a-z0-9][a-z0-9-]{0,31}`; `stable` is the default channel. |

The Game ID is derived from the developer key and slug only, so the same game
mirrored on several hosts has the same Game ID everywhere. A client MUST
recompute the Game ID from `developer_pubkey` and `slug` and reject a manifest
whose `game_id` does not match.

## 2. Chunking

* Files are split with content-defined chunking: FastCDC (2020 variant), with
  minimum 512 KiB, average 2 MiB, maximum 8 MiB. Chunk boundaries are a
  publisher-side optimisation: consumers MUST accept any chunk sizes between
  1 byte and 8 MiB (8 388 608 bytes) and MUST reject larger chunks.
* An empty file has an empty chunk list.
* Chunks are stored and served as raw bytes. A chunk's ID is always the hash of
  those raw bytes.
* Per-chunk `zstd` encoding is reserved for a future protocol revision. v0
  manifests MUST NOT carry an `encoding` member; v0 consumers MUST reject
  manifests that do (see `docs/decisions/0006-chunk-compression.md`).
  Transport-level compression (HTTP `Content-Encoding`) is always permitted.

## 3. Canonical JSON and signatures

Signed objects are JSON objects with a `sig` member.

* The signing input is the RFC 8785 (JCS) canonical serialisation of the
  object with the `sig` member removed, encoded as UTF-8.
* To keep canonicalisation trivial and unambiguous, signed objects MUST contain
  only integers in the range ±(2^53 − 1) as numbers. Non-integer numbers MUST
  be rejected.
* `sig` is the unpadded base64url encoding of the 64-byte Ed25519 signature.
* Verification MUST use strict Ed25519 verification (reject non-canonical
  signatures and small-order keys).

Unknown members in a signed object are covered by the signature (because the
signature is computed over the object as received) and MUST be ignored by
consumers that do not understand them.

### 3.1 Trust model

* The launcher pins `developer_pubkey` per Game ID at first install (trust on
  first use).
* Every release manifest MUST verify against the pinned key. A manifest signed
  by any other key MUST be refused unless (a) the user explicitly confirms the
  key change, or (b) a valid key-rotation statement (§4.4) links the pinned key
  to the new key.
* Because the Game ID is derived from the public key, a rotated key yields a
  new Game ID; rotation statements are what let a client carry an install over.
* Servers never hold developer private keys. Server API tokens only authorise
  uploads; they cannot forge releases.
* A client SHOULD refuse to move an install to a lower version than the one
  installed unless the user explicitly asks (rollback protection).

## 4. Objects

JSON Schemas for all objects live in [`schemas/`](schemas/).

### 4.1 Server info — `GET /.well-known/gamedist.json`

```json
{
  "protocol": "gamedist/0",
  "name": "Example Distributor",
  "api": "https://host.example/api/v0",
  "chunks": "https://cdn.example/chunks/",
  "tracker": "https://host.example/announce",
  "catalog": "https://host.example/api/v0/games",
  "registration": "open"
}
```

* `chunks` is a URL prefix ending in `/`; a chunk is fetched at `<chunks><id>`.
* `tracker` and `catalog` are optional. `registration` is `open`, `invite` or `closed`.

### 4.2 Game manifest — `GET /games/<slug>/manifest.json`

Generated by the server, **not signed**. It is a pointer document: it carries
presentation metadata and says which versions the channels point at. A client
MUST NOT trust it for integrity beyond checking that `game_id` matches
`developer_pubkey` + `slug` and that the key matches its pin.

```json
{
  "protocol": "gamedist/0",
  "game_id": "…",
  "slug": "cool-game",
  "developer_pubkey": "ed25519:…",
  "title": "Cool Game",
  "summary": "One-line pitch",
  "description_md": "…",
  "assets": { "icon": "<chunk id>", "banner": "<chunk id>", "screenshots": ["<chunk id>"] },
  "channels": { "stable": "1.2.0", "beta": "1.3.0-beta.1" },
  "releases": "https://host.example/games/cool-game/releases/",
  "rotations": []
}
```

Assets are single chunks (so at most 8 MiB each) fetched from the chunk
endpoint. `rotations` is an optional array of key-rotation statements (§4.4).

### 4.3 Release manifest — `GET /games/<slug>/releases/<version>.json`

Signed by the developer, immutable once published.

```json
{
  "protocol": "gamedist/0",
  "game_id": "…",
  "slug": "cool-game",
  "version": "1.2.0",
  "created": "2026-11-16T07:00:00Z",
  "changelog_md": "…",
  "platforms": {
    "windows-x86_64": {
      "launch": { "exe": "CoolGame.exe", "args": [], "cwd": "." },
      "files": [
        { "path": "CoolGame.exe", "size": 12345678, "mode": 493,
          "chunks": [ { "id": "<blake3>", "size": 2097152 } ] }
      ],
      "total_size": 12345678
    }
  },
  "developer_pubkey": "ed25519:…",
  "sig": "…"
}
```

Validation rules (consumers MUST enforce all of them before touching disk):

1. `protocol` is `gamedist/0`; `game_id` matches §1; `version` is valid.
2. Each file `path` is relative, uses `/` separators, is NFC-normalised and has
   no empty, `.` or `..` component, no backslash, no `:` (drive letters /
   alternate data streams), no control characters, no component ending in a
   space or dot, and no Windows reserved device name (`CON`, `NUL`, `COM1`, …).
3. Paths are unique within a platform, compared case-insensitively.
4. `size` equals the sum of the file's chunk sizes; `total_size` equals the sum
   of file sizes; every chunk size is in `1..=8388608`.
5. `mode` holds POSIX permission bits; only `0o755` (493) and `0o644` (420) are
   meaningful and other values are reduced to one of them by the executable bit.
6. `launch.exe` names a file in `files`. `launch.cwd` is `.` or a valid
   relative path. `launch.args` is a list of strings.

A release contains every platform of that version. Because releases are
immutable, all platforms of a version are published in one manifest.

### 4.4 Key-rotation statement

```json
{
  "protocol": "gamedist/0",
  "type": "key-rotation",
  "slug": "cool-game",
  "old_key": "ed25519:…",
  "new_key": "ed25519:…",
  "created": "2027-01-01T00:00:00Z",
  "sig": "…"
}
```

`sig` is made with **`old_key`**. A client that has `old_key` pinned and
receives a manifest for `new_key` MAY accept it without user confirmation if it
is given a valid statement (a chain of statements is followed link by link).
A lost or compromised old key cannot be rotated; that case falls back to the
explicit user confirmation.

### 4.5 Torrent — `GET /games/<slug>/releases/<version>-<platform>.torrent`

A BitTorrent v1 metainfo file generated by the server for the assembled install
tree of one platform.

* It is always a multi-file torrent whose `name` is `files`, with the files in
  manifest order, so that the BEP 19 web-seed URL
  `<host>/games/<slug>/releases/<version>/<platform>/` resolves each file to
  the HTTP file layout below.
* `url-list` contains that web-seed URL; `announce` is the server's tracker, if
  enabled.
* The torrent is **not** signed. Clients MUST verify the downloaded tree
  against the signed release manifest (chunk by chunk) before using it. The
  info hash is reported by `GET /api/v0/games/<slug>/releases`.

### 4.6 HTTP file layout (web seed)

`GET /games/<slug>/releases/<version>/<platform>/files/<path>` returns the
assembled file. Servers MUST support single-range `Range` requests.

## 5. REST API (`/api/v0`)

Errors are `application/problem+json` (RFC 7807) with `title`, `status`, `detail`.

### 5.1 Public

| Method | Path | Result |
|---|---|---|
| GET | `/games?page=&q=` | `{ "games": [game summary…], "page": 1, "pages": 3, "total": 51 }` |
| GET | `/games/{slug}` | game manifest |
| GET | `/games/{slug}/releases` | `{ "channels": {…}, "releases": [{ "version", "created", "platforms": [..], "torrents": { "<platform>": { "info_hash", "url" } } }] }` |
| GET | `/games/{slug}/releases/{version}` | signed release manifest |
| GET/HEAD | `/chunks/{id}` | raw chunk; `Cache-Control: public, max-age=31536000, immutable` |
| GET | `/export.jsonl` | one game manifest per line (catalog export for aggregators) |

The same documents are served outside `/api/v0` at the paths in §4.

### 5.2 Developer (`Authorization: Bearer <token>`)

| Method | Path | Body → result |
|---|---|---|
| POST | `/auth/register` | `{email, password, invite?}` → 201 |
| POST | `/auth/token` | `{email, password, name?}` → `{token}` |
| GET | `/dev/me` | account, keys, quota usage |
| POST | `/dev/keys` | `{pubkey, label?}` → 201 (200 if already registered) |
| POST | `/games` | `{slug, developer_pubkey, title, summary?, description_md?}` → game manifest |
| PATCH | `/games/{slug}` | any of `title, summary, description_md, assets` |
| POST | `/chunks/missing` | `{ids:[…]}` → `{missing:[…]}` (at most 10 000 ids) |
| PUT | `/chunks/{id}` | raw body; server verifies BLAKE3. 201 created, 204 already present |
| POST | `/games/{slug}/releases` | signed release manifest → 201 (200 if byte-identical re-publish) |
| POST | `/games/{slug}/channels` | `{channel, version}` |
| POST | `/games/{slug}/rotations` | key-rotation statement |
| DELETE | `/games/{slug}/releases/{version}` | unpublish; chunks are garbage-collected later |

The server MUST verify on release publish: schema, all §4.3 rules, the
signature, that `developer_pubkey` is the game's key, and that every referenced
chunk is present with the declared size.

### 5.3 Admin

`GET/POST /admin/users`, `GET /admin/games`, `GET/POST /admin/takedowns`,
`GET/POST /admin/settings`, `POST /admin/invites`, `GET /admin/audit`.
A taken-down game answers `451` on every public endpoint.

## 6. Client download procedure

1. Fetch server info and the game manifest; check the Game ID and key pin.
2. Resolve the channel to a version; fetch the release manifest; verify it.
3. Compute the set of chunks not already available locally (content store, or
   harvestable from the currently installed version).
4. Fetch them (HTTP chunk endpoint and/or torrent). Each chunk MUST be verified
   against its ID before it is written to its final location.
5. Assemble files in a staging directory, then swap them into place; on any
   failure restore the previous files.
