Game distribution that anyone can host

GameDist is three programs: a server anyone can run, a command-line tool developers use to publish builds, and a launcher players use to install and update games from any of those servers. Developers sign every release with their own key, so the server that hosts a game cannot change it.

Start with the part that is yours:

  • I play gamesInstall and update games by URL
  • I make gamesPublish signed builds to any server
  • I want to run a serverHost games for yourself or others

Three programs, three kinds of user

There is no central registry, no account system shared between servers, no DRM and no payment system. A game lives at an address like https://games.example.org/games/cool-game, on whichever servers its developer chooses.

For players

gamedist-launcher: a desktop app, plus a headless mode for scripts

  • Add a game by pasting its URL or opening a gamedist:// link. You do not need an account on the server.
  • On the first install the launcher remembers the developer's key. Every later release must be signed by that key, or the launcher stops and tells you.
  • Updates download only the chunks that changed. verify re-checks the installed files and re-downloads only the damaged parts.
  • Optionally download from other players over BitTorrent, and seed the games you have installed. Both are off by default.
  • Discover lists the catalogs of servers you add yourself. There is no default list.
$ gamedist-launcher --headless install \
    https://games.example.org/games/cool-game --dir ~/Games/cool-game
$ gamedist-launcher --headless update cool-game

The desktop app has only been run by hand on Linux and is not packaged yet. The headless launcher is covered by the end-to-end tests.

For game developers

gamedist: the publisher CLI, for your machine or CI

  • gamedist init creates an Ed25519 signing key on your machine. Servers never see it; they only check signatures made with it.
  • gamedist push splits the build into chunks, uploads only what the server lacks, and publishes a signed release. Pushing the same build again uploads nothing.
  • One release holds every platform, so Windows, Linux and macOS builds of a version go out together. Releases are immutable.
  • gamedist mirror copies your signed releases to another server. Launchers treat the copies as the same game.
  • Works in CI with an API token and an imported key.
$ gamedist init cool-game --title "Cool Game" \
    --server https://games.example.org
$ gamedist login https://games.example.org
$ gamedist game create --summary "One-line pitch"
$ gamedist push build/linux --platform linux-x86_64 \
    --exe CoolGame.x86_64 --version 1.0.0 --channel stable

Back up your key (gamedist key export). If you lose it, nobody can sign updates for your game, and players have to trust a new key by hand.

For server operators

gamedist-server: one binary with its own web portal

  • An embedded SQLite database and a local chunk directory. Put it behind a TLS reverse proxy and give it a public URL.
  • The built-in portal has a public catalog and game pages, a dashboard for developers (games, releases, channels, API tokens, keys) and admin pages.
  • Registration can be open, invite-only or closed. Per-account storage quotas, takedowns, an audit log and Prometheus metrics at /metrics.
  • Chunks never change once stored, so a CDN can cache them forever. Every release also gets a torrent, and the server runs an HTTP tracker.
  • The server holds no signing keys. If it is lost, developers publish their releases somewhere else.
$ gamedist-server  # local test: 127.0.0.1:8080, data in ./data
$ sudo ./deploy/install.sh --domain games.example.org \
    --email you@example.org

The server itself is covered by tests. The deployment files (install.sh, the Docker image, Compose with Caddy, the systemd unit) have not been tested end to end yet.

How it works

The developer signs; the server stores and serves; the launcher checks everything again on the player's machine, whichever way the bytes arrived.

  1. The developer creates a key. gamedist init generates an Ed25519 signing key that stays on the developer's machine. The Game ID is derived from that public key and the game's slug, so it is the same on every server.
  2. The build is chunked and signed. gamedist push splits every file into content-defined chunks of 512 KiB to 8 MiB, each named by its BLAKE3 hash, uploads only the chunks the server does not have, and signs a release manifest that lists every file and chunk for every platform.
  3. The server checks, then publishes. It verifies the signature and that every chunk is present, then serves the release over HTTP and as a BitTorrent torrent. Published releases cannot be changed.
  4. The launcher verifies everything again. It pins the developer key on first install, checks each release against the pinned key, downloads only the chunks it does not already have, verifies each one, and swaps the files into place atomically, rolling back on failure.

What a server can and cannot do

GameDist treats every server, CDN, mirror and peer as untrusted for the integrity of a game. Trust starts with the developer's key and is pinned by the launcher. That limits what a bad server can do, but does not remove every risk.

A server cannot

  • Change a release. Manifests are signed by the developer, and the launcher checks them against the key it pinned, not the key the server claims.
  • Swap the developer key quietly. A release signed by another key is refused, unless the old key signed a rotation statement or you accept the change yourself.
  • Get bad data installed. Every chunk is checked against its hash before it is written, whether it came over HTTP or BitTorrent. Torrents are not trusted on their own.
  • Roll back your install. The launcher will not move an installed game to a lower version unless you ask it to.
  • Hold developer keys. Servers only issue API tokens for uploads.

A server can still

  • Stop serving a game or go offline. Mirrors on other servers and other players help.
  • Hold back updates, or offer an older, genuinely signed version to someone installing for the first time.
  • Change the store page. Title, description and images are not signed. What gets installed is.
  • See who downloads what, by IP address. So can torrent peers and trackers when you use BitTorrent.
  • Make the first install count. The key is pinned on first use. If your first install comes from a server serving an impostor, the launcher pins the impostor's key. Compare the key the launcher shows with the one the developer publishes.

Games still run with your user's permissions: GameDist makes sure you run what the developer signed, not that the developer is benign.

Where the project stands

GameDist is pre-release software. Nothing has been published as a release yet. This summary follows the status table in the README, which is the authoritative and more detailed version.

Tested

Covered by the repository's tests, on Linux.

  • Protocol spec, JSON Schemas and the shared core library
  • Server API, chunk storage, web portal, developer dashboard, admin pages, quotas, takedowns, metrics
  • Publisher CLI: push, promote, mirror, key rotation
  • Headless launcher: install, delta update, verify and repair, key pinning and refusal of a changed key, downgrade refusal
  • BitTorrent: a second launcher gets at least half of a game from the first; fallback to HTTP
  • The same game from two servers shares one Game ID, pinned key and chunk store

Unverified

Implemented or configured, but not tested.

  • Desktop app: compiled and run by hand on Linux only; no automated tests
  • Anything on Windows or macOS: never built
  • gamedist:// link registration
  • Deploy files: install.sh, Docker image, Compose with Caddy, systemd unit
  • CI and release workflows: have not run yet
  • Wine runner for Windows builds; BitTorrent download and upload limits; the key-change dialog in the desktop app

Not implemented

Planned or possible later.

  • Desktop app packages in releases
  • Launcher self-update and code signing
  • S3 storage backend and PostgreSQL
  • UDP tracker and hybrid v2 torrents
  • Importing another server's catalog
  • Proton and Wine-GE detection

Bug reports, especially from Windows, macOS and real server deployments, are the most useful contribution right now. See CONTRIBUTING.md.
